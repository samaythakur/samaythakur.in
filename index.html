SmartQC: On-Device Visual Quality Inspection

Qualcomm | Snapdragon® AI Lab Build & Present Challenge
  • The problem:- I built SmartQC, an on-device visual quality inspection tool. The idea started from a problem I'd seen before — small food producers and workshops can't afford industrial inspection hardware, but the alternative, cloud-based AI inspection, has real downsides: latency, ongoing cost per scan, and sending production images off-site. So I set out to build something that ran entirely on-device, on hardware a small business might already own.
  • Building and validating the model:-I trained an image classifier — MobileNetV2 — on a labeled dataset of good and defective bread samples, using transfer learning so I didn't need to train from scratch. It reached 99.2% validation accuracy. But I didn't stop at accuracy — I ran a full evaluation: confusion matrix, precision, recall, and ROC-AUC, which came out to 0.9997. That mattered to me because accuracy alone can hide problems, like a model that's great on one class and bad on the other.
  • Making it deployment-ready:-I exported the model to ONNX and ran it through Qualcomm AI Hub, their cloud compilation service, to optimize it specifically for the Snapdragon X Elite chip. That gave me a genuinely deployment-ready model — not just a model that works in a notebook, but one compiled for real target hardware.
  • Turning results into product decisions:-Then I built an actual desktop app around it, and I made some deliberate product decisions here, not just engineering ones. For example, I added a confidence-threshold feature — if the model isn't confident, instead of forcing a guess, it flags the result as uncertain for manual review. I added that specifically after testing the model against a larger, messier batch of 352 real-world images and seeing it get a few genuinely ambiguous cases wrong — so I used that evaluation data to decide what feature to build next, rather than guessing.
  • Building for the real user, not just the demo:-I also added Grad-CAM explainability — a heatmap that shows which part of the image the model actually looked at — because for something like quality inspection, an operator won't trust a black-box yes/no answer. Being able to see 'here's the mold it detected' builds real trust in the tool. And I added batch processing with CSV export, because a real inspection workflow isn't one image at a time — someone would want to run a whole folder and get a report.
  • Results:-On the real-world batch test — 352 images the model hadn't seen — it got 97.4% right, correctly flagged the ambiguous ones instead of guessing wrong, and that gave me confidence the system would hold up outside a clean lab dataset.
  • Conclusion:-So end to end: I went from identifying a real gap — affordable, private, on-device inspection — to a trained and rigorously evaluated model, to a deployment-optimized build, to an actual usable application with features driven by what the evaluation data told me operators would need, all documented so someone else could reproduce or extend it.
  • Tech/Tools:-Python, PyTorch, ONNX, Qualcomm AI Hub, PyQt5, OpenCV, scikit-learn

CynLr EPM PoC

  • A program-management project built for an Engineering Program Manager internship application, requiring a technically complex robotics PoC — spanning object tracking and track-and-grasp capability — to be planned and coordinated across robotics, computer vision/ML, software, mechanical, electronics, procurement, and external vendor teams, with no existing execution structure to build from.
  • I structured the program into 41 top-level activities and 97 subtasks in Asana, mapping intra-project dependencies (camera calibration before tracking development, Phase 1 review before Phase 2 execution) and external dependencies (hardware vendors, procurement, robot library support). I built a 604 person-hour resource and effort estimation model in Excel, and designed a KPI framework with lead indicators (readiness, blockers resolved on time) and lag indicators (tracking/grasping performance, final acceptance). I also built in a progress-balancing mechanism so progress wasn't measured by task completion alone, but weighed against quality and integration readiness.
  • The hardest part wasn't listing tasks — it was reasoning about dependencies that weren't obvious on the surface, like recognizing that track-and-grasp (Phase 2) couldn't safely start until tracking reliability was proven in Phase 1, or that a procurement delay on an external component could silently block a CV milestone weeks downstream. Designing the KPI framework also forced a real tradeoff: measuring only task completion would have missed quality and integration readiness, so I built in a mechanism that weighs schedule, dependencies, and technical readiness together rather than just ticking boxes off a list.

AI-Based Bread Quality Indicator System

  • This was a hybrid embedded system built for real-time bread spoilage detection, combining an MQ-135 gas sensor and an ESP32-CAM with a MobileNetV2-based image classification model, with alerts delivered through LED/buzzer indicators and a Flask-based web dashboard.
  • The MQ-135 gas sensor continuously monitored spoilage-related gases — ammonia, CO₂, and volatile organic compounds — released as bread decomposed. Alongside this, the ESP32-CAM captured images for AI-based analysis, using a MobileNetV2 CNN trained on a Kaggle moldy-bread dataset (128×128 images, batch size 16, 15 epochs) to classify bread as fresh or moldy. When spoilage was detected, a red LED and buzzer activated; a green LED indicated fresh bread. A Flask web app provided live camera streaming and system status monitoring, with data transmitted over Wi-Fi — though the system could also run standalone without cloud or internet dependency.
  • In testing, gas sensor readings increased measurably as bread moved from fresh to spoiled, and the CNN model successfully differentiated fresh from moldy bread samples in image classification. Real-time alerts through the LED, buzzer, and web dashboard functioned as designed, and the system operated in standalone edge-AI mode without requiring continuous cloud connectivity.
  • Tech/Tools: Python, TensorFlow/Keras, MobileNetV2, Arduino IDE, ESP32-CAM, MQ-135 gas sensor, Flask

Stock Market Price Prediction & Analysis

  • This project built a complete data analytics and machine learning pipeline in Python to analyze and predict stock prices, using historical OHLCV data for the NIFTY 50 sourced via the yfinance API.
  • The pipeline covered the full data science workflow — data collection, preprocessing, and feature engineering of technical indicators including Moving Averages (MA20, MA50), RSI, MACD, and Bollinger Bands, followed by exploratory data analysis and multi-chart visualization using Matplotlib and Seaborn. A Long Short-Term Memory (LSTM) neural network was designed and trained to predict next-day closing prices from this feature set.
  • The model achieved a Mean Absolute Percentage Error (MAPE) of 1.39% and an R² score of 0.93 on the test set, evaluated against baseline forecasting models. Feature importance analysis found MA20 and MA50 to be the strongest contributing signals, followed by lagged close price, RSI, and MACD — validating the feature engineering approach. The model performed best during sustained trending markets and was comparatively weaker in sideways/choppy conditions, a known limitation of trend-following forecasting models.
  • Tech/Tools: Python, TensorFlow/Keras, LSTM, Pandas, NumPy, Scikit-learn, Matplotlib, Seaborn

Automatic Water Level Control System

  • Built during the CPS & IoT Intra-Institutional Internship - This project implemented an automated water level monitoring and pump-control system using an ultrasonic sensor with Arduino Uno, based on non-contact distance measurement of the water surface via ultrasonic wave reflection.
  • The system continuously measured water level and compared it against predefined upper and lower thresholds: when the level dropped below the lower threshold, the pump turned on to begin filling; when it reached the upper threshold, the pump turned off automatically. Built-in safety logic monitored for overflow and dry-run conditions, and sensor/pump faults, to keep the system reliable without manual supervision. Threshold-based control logic was implemented and tested in C/C++ across varying water-level conditions to validate correct ON/OFF automation.
  • As a further exploration, IoT-based remote monitoring concepts using ESP8266 were investigated as a path toward future integration — extending the system beyond standalone operation toward connected, remotely monitorable water management.
  • Tech/Tools: Arduino Uno, ESP8266, Ultrasonic Sensor, C/C++
